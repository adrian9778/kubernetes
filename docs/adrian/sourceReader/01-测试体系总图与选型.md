# 测试体系总图与选型

## 1. 质量体系不是一条流水线

Kubernetes 的质量保障至少有四个互相独立的维度：

| 维度 | 回答的问题 | 主要入口 |
|---|---|---|
| 行为正确性 | 函数、控制器、组件、集群是否按预期运行 | `make test`、`make test-integration`、Ginkgo e2e |
| 派生一致性 | 生成代码和规范是否能从源文件重复生成 | `make update`、`make verify` |
| API 契约 | API 是否兼容，生命周期、OpenAPI 和 discovery 是否一致 | `api/api-rules`、兼容性数据、OpenAPI verify、API integration/e2e |
| 交付完整性 | 二进制、镜像、tarball、vendor 与 staging 仓库是否完整 | `make cross`、`build/release.sh`、vendor verify、publishing rules |

只运行单测无法证明 API 兼容；只运行 `make verify` 也无法证明控制器行为正确。

## 2. 测试层级

### 2.1 同包单元测试

位置通常与被测文件同目录，文件名为 `*_test.go`。入口为：

```bash
make test WHAT=./pkg/kubelet GOFLAGS=-v
```

特点：

- 直接调用未导出函数和内部类型。
- 大量使用 table-driven case、fake clock、fake runtime、fake client、临时目录。
- 默认不启动 kube-apiserver 或真实 etcd。
- 最适合算法、校验、转换、队列状态、错误分支和并发状态机。

### 2.2 Integration

位置为 `test/integration/**`，入口为：

```bash
make test-integration WHAT=./test/integration/scheduler
```

特点：

- 通常启动真实 etcd 和 in-process API Server/control plane。
- 使用真实 REST、storage、watch、admission、controller 或 scheduler 组合。
- 比 e2e 更容易定位和重复，比单测更接近生产链路。

### 2.3 E2E

位置为 `test/e2e/**`。`hack/ginkgo-e2e.sh` 找到构建好的 `ginkgo` 与 `e2e.test`，准备 provider、读取 kubeconfig，然后把 Ginkgo 参数与 suite 参数传给测试二进制。

特点：

- 面向已经运行的 Kubernetes 集群。
- 从公开 API 和用户可观察行为验证系统。
- 覆盖跨组件、节点、网络、存储、升级和一致性场景。

### 2.4 E2E Node

位置为 `test/e2e_node/**`，入口为 `make test-e2e-node` 和 `hack/make-rules/test-e2e-node.sh`。

特点：

- 重点验证 kubelet、CRI、cgroup、设备、驱逐、probe、volume、节点资源管理。
- 可本机运行，也可通过 `test/e2e_node/remote` 在远端主机运行。
- 对操作系统、root 权限、容器运行时、内核功能高度敏感。

### 2.5 性能与 Soak

性能不是单独的一层目录，而是按被测边界分布：

- `test/integration/scheduler_perf`：调度器吞吐、延迟和配置化 workload。
- `test/integration/ipamperf`：IPAM 性能。
- `test/integration/benchmark`：日志提取、结果转换等 benchmark 工具。
- `test/e2e/framework/perf`：集群 e2e 性能测量工具。
- `test/e2e_node/perf`：节点工作负载，例如 NPB、PyTorch workload。
- `test/soak/serve_hostnames`：长时间运行的 hostname 服务样例。

## 3. `make test` 的真实执行链

```text
Makefile:test/check
  -> hack/make-rules/test.sh
  -> kube::golang::setup_env
  -> find_go_packages
  -> go list 所有 workspace module
  -> 排除特殊测试包
  -> normalize_go_targets
  -> gotestsum -> go test
  -> 可选 JSON/JUnit/coverage 汇总
```

关键默认值：

- `KUBE_RACE=-race`，显式设为空可关闭。
- `KUBE_TIMEOUT=-timeout=180s`。
- `KUBE_CACHE_MUTATION_DETECTOR=true`，捕捉 informer cache 对象被原地修改。
- `KUBE_PANIC_WATCH_DECODE_ERROR=true`，把 watch 解码错误视作编程错误。
- `PARALLEL=-1` 交给 Go 自行决定包并发；可通过 `-p` 修改。
- `KUBE_JUNIT_REPORT_DIR` 或 `ARTIFACTS` 控制 JUnit 产物。
- `KUBE_COVER=y` 开启覆盖率，`KUBE_COVERMODE` 默认 `atomic`。

默认排除项包括：

- `test/e2e`
- `test/e2e_dra`
- `test/e2e_node/**`
- `test/e2e_kubeadm/**`
- 各 staging 模块的 `test/integration/**`
- `cmd/kubeadm/test/**`

因此“全量 `make test` 通过”不能推出 e2e 或 integration 通过。

## 4. 如何为改动选测试

| 改动 | 最低测试 | 常见追加测试 | 还要运行的生成/校验 |
|---|---|---|---|
| 纯函数、解析、校验 | 同包 table test | fuzz、边界与错误注入 | gofmt、typecheck |
| controller reconcile | 同包 fake client/informer | 对应 integration controller | verify、必要时 codegen |
| scheduler plugin | plugin 单测 | scheduler integration、scheduler_perf | 配置 API 变更时 codegen/OpenAPI |
| kubelet/CRI/volume | 同包 fake runtime | e2e_node | feature gate、平台构建校验 |
| API 字段 | default/conversion/validation 单测 | API integration、discovery/OpenAPI e2e | codegen、OpenAPI、compatibility data |
| admission/auth/storage | 同包单测 | integration controlplane/auth | API/feature gate verify |
| kubectl 行为 | 同包单测与 fixtures | cmd test、相关 e2e | generated docs 如受影响 |
| vendor 依赖 | 受影响包单测 | integration/build | update-vendor、verify-vendor/licenses |
| release 脚本 | shell/目标级测试 | cross build、package dry run | verify shellcheck/dependencies |

## 5. 决策原则

1. 先找到最小的状态边界。纯函数不要用 e2e 验证。
2. 如果行为依赖 REST storage、watch resourceVersion、admission 或真实序列化，fake client 不够，至少写 integration。
3. 如果行为依赖 kubelet、内核、CRI、挂载或设备插件，必须考虑 e2e_node。
4. 如果用户可见契约跨越多个组件，补 e2e。
5. 如果改了 API 源类型，即使业务测试全绿，也必须完成生成与兼容性闭环。
