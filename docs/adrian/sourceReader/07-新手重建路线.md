# 从零重建最小 Kubelet 与 kube-proxy

## 1. 原则

不要一开始实现 CRI、CNI、CSI、iptables 四件套。先定义状态机和接口，再用内存 fake 跑通收敛。每阶段都要求：重复调用结果不变；进程重启可恢复；外部调用超时后不会把“不确定”误报为成功；旧事件不能覆盖新状态。

## 2. 第一阶段：最小 Pod 执行器

定义 `PodSpec{UID, Containers, Grace}`、`Runtime` 接口和 `RuntimePodStatus`。实现内存 fake runtime。实现 `SyncPod(desired, actual)` 纯函数，输出 actions：CreateSandbox、Start、Stop、Remove。再实现 executor。

验收：创建双容器 Pod；第二次 sync 不产生动作；删除一个 runtime container 后能补建；spec hash 改变只重启对应容器；sandbox 配置改变重建整个 Pod。

## 3. 第二阶段：每 Pod worker 状态机

全局 map 以 UID 保存 worker；每 UID 一个容量 1 的通知 channel；状态对象保存 active/pending update、working、terminating、terminated、finished；更新只合并数据，worker 串行取走。加入定时队列和指数 backoff。

验收：100 次并发 update 不并发调用同 UID runtime；不同 UID 可并发；kill 到达后普通 update 不能回到 running；grace 只能缩短；worker panic/错误后可重试。

## 4. 第三阶段：观察环与缓存

实现每秒 List runtime 的 GenericPLEG，对比 old/new 生成 start/die/remove 提示。事件只触发重新 sync，不携带权威完整状态。实现带时间戳 runtime cache，并允许 PLEG 主动刷新。

验收：故意丢掉一个事件，下一次 relist 仍收敛；重启 agent 后从 runtime 重建 orphan Pod；runtime List 超时期间不删除未知 Pod。

## 5. 第四阶段：状态上报

实现 `map[UID]{status,version}`、容量 1 dirty channel 和单同步 goroutine。写 API 成功才推进 apiVersion，失败保留 dirty。把 readiness、started 和终止状态都通过同一更新函数合并。

验收：API 连续失败 10 次后恢复，最终提交最新版本而非逐条旧版本；旧 Pod UID 不能覆盖同名新 Pod；finished 但清理未完成时不可删除 API 对象。

## 6. 第五阶段：探针

为每 `(UID, container, type)` 建 worker；实现 initial delay、period、timeout、success/failure threshold。startup 成功前屏蔽其他 probes。readiness 只改流量状态，liveness/startup 失败触发 pod sync 而非直接 kill。

验收：容器 ID 改变会清旧结果；终止时停止 liveness/startup 但 readiness 可先下线；探针风暴通过随机初始延迟摊平。

## 7. 第六阶段：卷双缓存

先只实现 hostPath/tmpfs fake：DSW 来自 Pod，ASW 来自成功操作；reconciler 顺序为 unmount pod、mount、unmount device、detach；operation executor 对同 key 去重并 backoff。增加 uncertain 状态和启动目录扫描。

验收：mount 返回 timeout 进入 uncertain；重启后扫描恢复；Pod 删除必须等 volume unmount；两个 Pod 共享 volume 时删除一个不会 detach。

## 8. 第七阶段：资源与 checkpoint

先实现 CPU static：default set + `(UID,container)->cpuset`；写 JSON + checksum + atomic rename；启动校验 policy/topology；周期 reconcile 到 fake runtime。随后扩展 NUMA hints、memory blocks、device allocation。

验收：checkpoint 损坏时拒绝启动 static policy；sources ready 前不清 stale；运行时 cpuset 被外部篡改后可恢复；分配失败不留下半条记录。

## 9. 第八阶段：驱逐

实现 Observation、Threshold、firstObservedAt、grace、minReclaim 和 node condition 防抖。先 node reclaim，再按 request/priority/usage 排序，每轮只 kill 一个，并进入统一 pod worker kill 路径。

验收：瞬时压力不触发 soft eviction；hard eviction 立即执行；达到 minReclaim 前 pressure 不清除；critical Pod 不驱逐；驱逐状态明确为 Evicted。

## 10. 第九阶段：proxy 公共图

定义 ServicePort 和 Endpoint，按 family 构建 `ServicePortMap/EndpointsMap`。实现 Slice cache 和 `CategorizeEndpoints`。先输出抽象规则 JSON，不碰真实内核。

验收矩阵至少包含 ClusterIP/NodePort/LB × internal/external Cluster/Local × 有无 local endpoint × Ready/Serving/Terminating × IPv4/IPv6。特别验证：有远端 endpoint 但 Local 为空是 DROP；完全无 endpoint 是 REJECT；无 Ready 时可回退 Serving+Terminating。

## 11. 第十阶段：一个真实网络后端

Linux 新实现优先 nftables：固定 table/base chains；map VIP tuple 到 service chain；service chain 选择 endpoint；endpoint chain DNAT；transaction 原子提交；保存 previous keys 并删除 leftovers；周期 full sync。若环境只支持 iptables，则生成完整 restore 文本一次提交。

验收：重复 sync 无差异；中途失败不留下半套规则；手工删除 table 后 full sync 恢复；Service/Endpoint 删除后无陈旧 chain/map key；UDP endpoint 删除清 conntrack；双栈两套图完全隔离。

## 12. 最终端到端时序

```text
API Pod ADD
 -> podManager
 -> podWorkers.UpdatePod
 -> SyncPod
 -> resource Allocate/checkpoint
 -> volume DSW -> reconciler -> ASW
 -> CRI RunSandbox/Create/Start
 -> PLEG observes start
 -> runtime cache refresh
 -> probe workers publish readiness
 -> status manager Patch Ready
 -> EndpointSlice controller 生成 endpoint
 -> kube-proxy informer
 -> change tracker
 -> bounded sync
 -> kernel rule/LB object
 -> Service 流量到 Pod
```

删除时沿反方向收敛，但不是简单倒序：readiness/EndpointSlice 应先退出流量，容器按 grace 终止，卷和资源最后释放，API Pod 只有在节点内容安全后才可删除。

## 13. 调试清单

每个故障先问：期望对象是否进入本地 cache；负责该对象的 worker 是否被唤醒；worker 当前 phase 是什么；外部动作是否成功还是 uncertain；观察环是否看到新现实；状态 version 是否成功提交；若是网络，目标图是否正确、内核提交是否成功、旧 conntrack 是否仍存在。沿所有权查，不要沿日志关键词随机漫步。
