# 新手重建顺序与验收清单

本章不是要求一开始复制 Kubernetes 的全部代码，而是按依赖关系重建一个功能等价的最小系统。每一阶段都给出“能继续下一步”的验收条件。

## 阶段 1：对象模型与 Scheme

实现：

- TypeMeta、ObjectMeta、ListMeta。
- GVK、GVR、namespaced/cluster scope。
- runtime.Object 与 DeepCopyObject。
- Scheme：类型注册、GVK 查找、default、conversion。
- JSON codec。

验收：

- 外部 v1 对象可 decode、default、转 internal、再转回 v1。
- round-trip 后语义相等。
- 未注册 GVK 返回具体错误。
- deep copy 后修改副本不影响原对象。

## 阶段 2：存储与 Watch

实现：

- 内存 KV，随后替换为 etcd。
- revision/resourceVersion。
- CRUD、CAS update、list、watch。
- label/field selector 的最小实现。

并发状态机：

```text
Create -> revision+1 -> persist -> broadcast Added
Update(expectedRV)
  -> RV 相等: revision+1 -> Modified
  -> RV 不等: Conflict
Delete -> tombstone/revision+1 -> Deleted
Watch(startRV) -> replay/stream -> compacted 时 Gone
```

验收：并发更新只有一个成功；watch 不丢失已承诺事件；慢消费者不会锁死写路径。

## 阶段 3：API Server

实现：

- REST routing 与 content negotiation。
- authentication、authorization 接口。
- mutating/validating admission 链。
- REST strategy 与 storage。
- `/readyz`、discovery、OpenAPI。

请求顺序必须可测试：

```text
authenticate
 -> authorize
 -> decode/default/convert
 -> mutating admission
 -> validation
 -> validating admission
 -> storage transaction
 -> convert/encode response
```

验收：错误映射到稳定 HTTP status/reason；API 出现在 discovery 和 OpenAPI；ready 前拒绝测试流量。

## 阶段 4：Client、Fake、Informer 与 Queue

实现：

- typed REST client。
- fake action/reactor/object tracker。
- reflector list-watch。
- DeltaFIFO。
- thread-safe indexer。
- shared informer fan-out。
- rate-limiting workqueue。

Informer 状态机：

```text
List -> Replace store -> initial sync
 -> Watch
 -> event -> DeltaFIFO -> HandleDeltas
 -> update indexer -> callback
watch error -> backoff -> relist
```

验收：断开 watch 后可恢复；同一 key 合并更新；handler 慢时不破坏 cache；从 cache 取出的对象不得原地修改。

## 阶段 5：Controller

先实现 ReplicaSet 风格控制器：

```text
informer event -> enqueue key
worker -> cache Get -> reconcile desired/current
 -> create/delete child
 -> update status
error -> rate-limited retry
success -> Forget
```

验收：重复 reconcile 幂等；Conflict 可重试；删除时处理 tombstone；进程重启后仅靠 API 状态恢复。

## 阶段 6：Scheduler

实现：

- pending queue、backoff queue、unschedulable pool。
- node snapshot/cache。
- Filter、Score、Reserve、Permit、PreBind、Bind、PostBind 扩展点。
- assume cache 与异步 bind。
- preemption 的候选计算。

调度周期：

```text
Pop Pod
 -> snapshot
 -> PreFilter/Filter
 -> 无节点: PostFilter/preemption -> requeue
 -> Score/NormalizeScore
 -> select host
 -> Assume
 -> Reserve/Permit/PreBind
 -> Bind
 -> FinishBinding/PostBind
 -> 成功 Forget；失败 Unreserve/forget assume/requeue
```

当前树涉及 PodGroup/gang scheduling 时，还需增加 group 准入、最小成员数、permit 等待、整体失败回滚和 group preemption。

验收：并发调度不重复绑定；assume 失败可回滚；节点/Pod 更新会激活正确队列；group 不会半提交。

## 阶段 7：Kubelet 与 CRI

实现：

- Pod source 合并。
- pod worker，每 Pod 串行同步。
- desired/actual state。
- CRI runtime/image client。
- volume manager、probe manager、PLEG。
- status manager。

核心状态机：

```text
Pod config -> pod worker
 -> admit
 -> mount volumes
 -> create sandbox
 -> create/start init containers
 -> create/start app containers
 -> probes/PLEG observe
 -> update PodStatus
delete -> graceful stop -> unmount -> remove sandbox
```

验收：同一 Pod 不并发 sync；runtime 短暂失败会退避；进程重启后能从 runtime 重建状态；静态 Pod/mirror Pod 关系稳定。

## 阶段 8：分层测试体系

建立顺序：

1. 每个包 table-driven 单测。
2. fake clock/runtime/client 与 reactor。
3. 嵌入式 etcd integration framework。
4. API/controller/scheduler integration。
5. 单节点 e2e_node harness。
6. 多组件集群 e2e。
7. perf 与 soak。

验收：每个 bug 都能在最低可复现层增加回归测试；没有用 e2e 掩盖可单测的算法，也没有用 fake 验证只有真实 storage 才有的语义。

## 阶段 9：生成与兼容性

实现一个最小生成系统：

- 根据类型标记生成 deep copy、conversion、client。
- 从类型生成 OpenAPI。
- 保存 API compatibility snapshot。
- verify 在临时树重跑生成器并比较 diff。

验收：删除一个生成文件后 update 可恢复；手改生成文件后 verify 失败；破坏兼容字段后 compatibility check 失败。

## 阶段 10：构建与发布

实现：

- 可复现版本注入。
- 多平台 cross build。
- 最小 server/node/client tarball。
- OCI 镜像。
- 本地 provider 的 up/down/prepare-e2e。
- staging 模块拆分和依赖拓扑发布。

验收：从干净 checkout 只按文档命令生成相同文件集；目标平台启动；cluster up/e2e/log dump/down 闭环；独立模块不反向依赖主仓私有包。

## 最终改动验收模板

每次实现功能，记录：

```text
源码真相：修改了哪些非生成文件
行为契约：成功、失败、重试、取消、并发分别是什么
最低测试：哪个同包测试覆盖核心算法
真实边界：是否需要 etcd/API Server/CRI/集群
生成闭环：运行哪些 update，预期产生哪些 diff
兼容性：旧对象、旧客户端、旧 storage version 如何处理
发布影响：哪些 binary/image/tarball/staging repo 变化
证据：JUnit、artifact、benchmark、compatibility diff
```

## 当前树建议命令速查

```bash
# 单包单测
make test WHAT=./pkg/scheduler GOFLAGS=-v

# 单个 integration 包或用例
make test-integration WHAT=./test/integration/scheduler GOFLAGS=-v
make test-integration WHAT=./test/integration/pods \
  KUBE_TEST_ARGS='-run ^TestName$'

# 精确生成与校验
hack/update-codegen.sh
hack/update-openapi-spec.sh
hack/update-generated-api-compatibility-data.sh
make verify WHAT="gofmt typecheck"

# 构建
make all WHAT=cmd/kube-apiserver
make all WHAT=cmd/kubelet DBG=1

# 依赖变更
hack/pin-dependency.sh <module> <version>
hack/update-vendor.sh
```

这些命令是流程入口，不应盲目全跑。先按改动边界选择最小集合，再向真实边界逐层扩大。
