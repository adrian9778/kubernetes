# 01. 项目地图与阅读方法

## 1.1 先认识系统边界

API Server 是状态入口，不负责副本扩缩和容器启动；Controller Manager 负责期望状态收敛；Scheduler 只做放置决策；Kubelet 只执行分配给本节点的工作负载；Kube Proxy 把 Service/EndpointSlice 编译成节点网络规则。组件之间以 API 对象协作，而不是互相调用内部 Go 函数。

这种架构允许组件独立重启。进程内缓存可以丢，API 对象、etcd 数据、runtime 现实和必要 checkpoint 不能依赖某个 goroutine 永久存活。

## 1.2 顶层目录

| 目录 | 职责 | 推荐读法 |
|---|---|---|
| `cmd` | 二进制入口、flags、Options、Config、Run | 从 main 追到阻塞点 |
| `pkg/apis` | 内部 API 类型、conversion、default、validation | 选一个 group 纵向阅读 |
| `pkg/registry` | 原生资源 REST storage 与 strategy | 配合 API Server 阅读 |
| `pkg/controller` | 具体控制循环 | 先 ReplicaSet，再复杂控制器 |
| `pkg/scheduler` | 队列、缓存、调度周期、插件实现 | 沿 ScheduleOne 阅读 |
| `pkg/kubelet` | 节点收敛、runtime、probe、status、资源 | 沿 syncLoop/syncPod 阅读 |
| `pkg/proxy` | Service/Endpoint 到内核规则 | 沿 syncProxyRules 阅读 |
| `pkg/volume` | in-tree volume 与 CSI 协作 | 按插件接口和 manager 阅读 |
| `staging/src/k8s.io` | 对外发布的共享模块权威源码 | 先模块边界，再读接口 |
| `test` | integration、e2e、node、perf、fuzz | 用测试确认行为语义 |
| `hack` | update、verify、生成和开发脚本 | API/依赖改动必读 |
| `build` | 容器化构建、镜像、发布包 | 沿 release 目标阅读 |
| `cluster` | 历史 provider 集群脚本、addons | 学习部署编排，不作为新架构模板 |
| `vendor` | 固化依赖 | 不直接修改 |

## 1.3 staging 为什么特殊

`staging/src/k8s.io` 是 `k8s.io/*` 模块的源代码，不是复制品。`client-go`、`apimachinery`、`apiserver`、`kube-scheduler`、`kubelet`、`cri-api`、`dynamic-resource-allocation` 等在 monorepo 中协同开发，再由 publishing bot 发布到独立仓库。

依赖方向受 `staging/publishing/import-restrictions.yaml` 约束。staging 模块不能反向 import `k8s.io/kubernetes`，否则独立发布后无法构建。

## 1.4 控制循环的五个问题

阅读任意模块时记录：

1. 谁创建核心对象？
2. 输入事件从哪里来？
3. 哪些字段被锁保护，哪些对象只读共享？
4. 错误如何分类、退避和恢复？
5. context 取消后按什么顺序停止？

例如 ReplicaSet Controller：Controller Manager 创建；RS/Pod Informer 提供事件；Indexer 只读共享、queue 自己加锁；API 暂时错误 AddRateLimited；停止时关闭 queue 并等待 workers。

## 1.5 一条标准事件链

```text
etcd revision
 -> API watch cache
 -> HTTP watch stream
 -> client-go Reflector
 -> DeltaFIFO
 -> Informer Store/Indexer
 -> event handler
 -> workqueue key
 -> worker
 -> Lister 获取最新对象
 -> reconcile
 -> client 写回 API
```

事件仅用于“提醒可能有变化”，不是业务命令。队列存 key 而非完整对象，worker 必须重新读缓存，才能合并快速连续更新。

## 1.6 阅读代码的实际步骤

1. 从 `cmd/<component>/<main>.go` 找命令构造。
2. 在 `cmd/<component>/app` 找 `Run` 和 config 创建。
3. 找核心 struct 的构造函数，列出字段依赖。
4. 找长期运行的 `Run`、loop、worker。
5. 沿一个具体事件走完整成功路径。
6. 再读 NotFound、Conflict、timeout、shutdown 路径。
7. 最后读相邻测试，用测试表格确认边界语义。

## 1.7 “所有源码”的合理覆盖方式

仓库包含数千个 Go 文件，大量内容是同一模式的不同资源、平台或生成版本。文档采用“机制精读 + 目录索引”：每类机制精读代表实现，其余源码说明职责、接口和进入条件。逐行重复解释生成 client 或每个 registry strategy，不会帮助重建系统。

## 1.8 新手常见误区

- 把 API Server 当业务控制器。
- 把 informer cache 当强一致数据库。
- 直接修改 Lister 返回的对象。
- 认为 watch 永远不丢事件。
- 把 Event 当可靠业务消息队列。
- 把 feature gate 打开等同于 API 已稳定。
- 先啃生成代码，没看类型和生成器输入。
