# 从零重建控制器与调度器

目标不是一次复制 Kubernetes，而是按可验证的阶段重新实现同类机制。每阶段都只引入一个新的分布式系统问题。

## 阶段 1：通用控制器运行时

先定义：

```go
type Reconciler interface {
    Sync(ctx context.Context, key string) error
}

type Controller struct {
    queue  RateLimitingQueue[string]
    lister ObjectLister
    client APIClient
}
```

实现 informer store、`namespace/name` key、去重队列、多个 worker、`Get/Done/Forget/AddRateLimited`、cache sync barrier 和 context shutdown。

验收：同 key 连续 Add 100 次最多合并为有限次 sync；sync 进行中再次 Add 会在 Done 后再执行；两个 worker 不同时处理同 key；失败指数退避，成功清空退避历史；关闭时 worker 全部退出。

## 阶段 2：ReplicaSet

对象只需 `spec.replicas`、selector、Pod ownerRef、status。实现 claim/adopt/release 和 UID 校验，再实现 expectations。

伪代码：

```text
sync(rsKey):
  rs = lister.Get(key)
  pods = indexer.ByOwnerUID(rs.uid) + orphanCandidates
  claimed = claim(pods, rs.selector)
  if expectations.satisfied(key):
      diff = active(claimed) - rs.replicas
      diff < 0: expectCreate(-diff); slowStartCreate()
      diff > 0: chooseDelete(diff); expectDelete(keys); parallelDelete()
  updateStatus()
```

验收：API 创建成功但 informer 延迟时不重复创建；创建失败会降低 expectation；同名 RS 删除重建不会领养旧 UID Pod；controller 删除中不领养孤儿。

## 阶段 3：Deployment

只管理 ReplicaSet，不直接创建 Pod。实现 template hash、revision、RollingUpdate 的 maxSurge/maxUnavailable 和 Recreate。

验收：replicas=10、maxSurge=2 时总 Pod 不超过 12；available 不低于 10-maxUnavailable；暂停后不推进 revision；Recreate 在旧 Pod 真正消失前不扩新 RS；回滚能选择历史 RS template。

## 阶段 4：StatefulSet

增加 ordinal、稳定 DNS 名、每 ordinal PVC、ControllerRevision、OrderedReady/Parallel、partition 和 retention policy。把每个 Pod 明确建模为 `Missing -> Pending -> RunningNotReady -> Available -> Updating/Condemned -> Terminating`。

验收：OrderedReady 下 Pod 0 未 Ready 时不创建 Pod 1；缩容先删最高 ordinal；Pod 重建保持名称/PVC；partition 以下 ordinal 不更新；控制器崩溃重启后可从对象状态继续。

## 阶段 5：Job

先做 NonIndexed，再增加 Indexed、backoff、FailurePolicy、SuccessPolicy。必须实现 `uncountedTerminatedPods + tracking finalizer` 协议。

验收：在“status 写成功后崩溃”和“finalizer 删除成功后崩溃”两个注入点重启，成功/失败计数都恰好一次；同 index 的重复 Pod 不重复计数；FailIndex 不错误终止其他 index。

## 阶段 6：删除协议

实现 owner graph 和 finalizer：

```text
metadata watch -> UID graph -> verify owner from API
  -> dangling: background delete
  -> foreground: dependent 清空后移除 owner finalizer
  -> orphan: patch dependents ownerRefs 后移除 finalizer
```

再实现 Namespace deleter：discovery GVR、DeleteCollection fallback、重新 list、remaining estimate、conditions、finalize。

验收：同名 owner 重建不误认；跨 namespace 非法 ownerRef 不形成有效所有权；dependent 自带 finalizer 时 foreground owner 保持 Terminating；有未知/新增 GVR 时 Namespace 仍可通过 discovery 清理。

## 阶段 7：EndpointSlice 与 Volume

EndpointSlice 先实现 Service selector 到 endpoint 集合，再实现按容量切片、tracker RV、防陈旧缓存、batch delay 和 topology hints。

Volume 先实现静态 PV/PVC 双向绑定，再实现 dynamic provisioning 和 reclaim。Attach/Detach 使用 DSW、ASW、operation executor，周期 reconcile，不把 API 操作塞进 informer handler。

验收：EndpointSlice 被用户误删后恢复；旧 RV 不导致重复 slice；PV/PVC 任一绑定写之后崩溃可恢复；不支持 multi-attach 的卷不会同时附着两节点。

## 阶段 8：经典单 Pod Scheduler

数据结构顺序：

1. activeQ：priority heap。
2. backoffQ：按 backoff deadline 的 heap。
3. unschedulable pool：Pod key 到失败信息。
4. cache：nodeName 到 NodeInfo、Pod UID 到状态。
5. snapshot：每周期稳定读视图。

执行顺序：

```text
Pop -> Snapshot -> PreFilter -> parallel Filter -> PreScore/Score
    -> Assume -> Reserve -> Permit -> async binding
    -> PreBind -> Bind -> PostBind
```

每个正向动作都写出补偿：Reserve/Unreserve、Assume/Forget、Permit wait/reject。用 race detector 测试 queue/cache；用 fake clock 测 backoff；用 fake client 注入 Bind 失败。

## 阶段 9：Preemption

在 Snapshot 副本上删除低优先级 Pod并重跑 Filter。加入 PDB violation 统计和候选排序。执行时先处理 waiting/prebind 内存 victim，再走 API delete；preemptor 只写 nominatedNodeName 并重新入队。

验收：高优先级 Pod 不抢占同优先级；PDB violation 更少的节点优先；删除 victim 失败时不假装抢占成功；victim 删除事件早到不会让 preemptor 永久卡住。

## 阶段 10：v1.37 工作负载调度

最后才实现 PodGroup。把队列元素抽象为 Entity；维护 group forest；在可变 Snapshot 中尝试 placement；每个 Pod assume/reserve 返回 revert closure；父组失败时逆序回滚整棵子树。再增加 PodGroupPostFilter 和 workload-domain preemption。

验收：组中任一 Pod 不可行时没有成员泄漏到真实 cache；父 CompositePodGroup 失败会使已成功子组失效；回滚逆序调用全部 Unreserve；组重试保持公平 timestamp；feature gate 关闭时经典 Pod 路径不受影响。

## 推荐测试矩阵

| 层次 | 测试 |
|---|---|
| 纯函数 | selector、diff、ordinal、状态转换、候选排序 |
| fake clock | expectation timeout、queue backoff、grace period |
| fake client | conflict、NotFound、部分写成功、限流 |
| fake informer | tombstone、乱序、重复事件、旧 RV |
| 并发 | 同 key 去重、锁竞争、shutdown、异步回调早到 |
| integration | 真 API Server/etcd 下 owner/finalizer/status 子资源 |

## 最重要的重建原则

- 本地缓存是观察结果，不是提交日志。
- API 返回成功后，必须考虑 informer 尚未观察到写入。
- reconcile 要从当前状态重新计算，不依赖上一次内存步骤仍存在。
- 名称可复用，UID 才是对象身份。
- 删除是协议；DeletionTimestamp、ownerReference、finalizer 和 GC 共同决定完成时刻。
- 所有异步正向步骤都要有补偿或可幂等重放。
- 先实现单 Pod/单控制器稳定路径，再开启 v1.37 的 PodGroup、ConsistencyStore 和异步 API 分支。
