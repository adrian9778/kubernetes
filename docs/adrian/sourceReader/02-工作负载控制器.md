# Deployment、ReplicaSet、StatefulSet 与 Job

## 1. Deployment：管理 ReplicaSet，不直接管理 Pod

核心类型 [`DeploymentController`](../../../pkg/controller/deployment/deployment_controller.go#L67)，构造函数 [`NewDeploymentController`](../../../pkg/controller/deployment/deployment_controller.go#L104)，主同步函数 [`syncDeployment`](../../../pkg/controller/deployment/deployment_controller.go#L574)。

事件映射：

| 事件 | 处理 |
|---|---|
| Deployment add/update/delete | 自身 key 入队 |
| ReplicaSet add/update/delete | 解析 controllerRef 或 selector，找到 Deployment 入队 |
| Pod delete | Pod -> RS -> Deployment，用于 Recreate 判断旧 Pod 是否消失 |

`syncDeployment` 的状态机：

```text
按 key 读 Deployment
  -> 已删除：清理 expectations/consistency state
  -> selector 为空：只更新失败状态
  -> 列出并 claim ReplicaSets
  -> deletionTimestamp != nil：syncStatusOnly
  -> paused：checkPausedConditions + sync
  -> rollback annotation：rollback
  -> 是否纯扩缩容事件：scale
  -> strategy=Recreate：rolloutRecreate
  -> strategy=RollingUpdate：rolloutRolling
```

RollingUpdate 在 [`rolloutRolling`](../../../pkg/controller/deployment/rolling.go#L31) 中先协调新 RS，再协调旧 RS。扩容上界来自 `replicas + maxSurge`；缩容前必须满足最小可用数 `replicas - maxUnavailable`。旧的 unhealthy replicas 优先清理，避免不可用 Pod 占用 rollout 预算。

新 RS 在 [`getNewReplicaSet`](../../../pkg/controller/deployment/sync.go#L146) 构造，PodTemplate hash 同时进入 RS selector、template label 和名称后缀。这样旧、新 revision 不会选择到彼此的 Pod。ControllerRevision 不是 Deployment 的历史载体；Deployment 历史就是一组带 revision annotation 的 ReplicaSet。

Recreate 在 [`rolloutRecreate`](../../../pkg/controller/deployment/recreate.go#L29) 先把旧 RS 缩为 0，等待旧 Pod 真正消失，再扩新 RS。只看旧 RS 的 `spec.replicas=0` 不够，因为 Pod 删除有 grace period。

## 2. ReplicaSet：数量控制的标准模板

核心类型 [`ReplicaSetController`](../../../pkg/controller/replicaset/replica_set.go#L97)，主同步 [`syncReplicaSet`](../../../pkg/controller/replicaset/replica_set.go#L755)，增删逻辑 [`manageReplicas`](../../../pkg/controller/replicaset/replica_set.go#L649)。

同步步骤：

```text
EnsureReady(consistencyStore)
  -> lister.Get(RS)
  -> expectations.SatisfiedExpectations
  -> FilterPodsByOwner：按 owner UID 索引取直属 Pod + orphan
  -> FilterActivePods
  -> ClaimPods：adopt/release
  -> 若 expectations 满足且 RS 未删除，manageReplicas
  -> 计算并更新 status
  -> 需要时 AddAfter(minReadySeconds)
```

少 Pod 时，先 `ExpectCreations(diff)`，再用 [`slowStartBatch`](../../../pkg/controller/replicaset/replica_set.go#L887) 按 1、2、4、8... 批量并发创建。某批失败即停止后续批次，避免 quota 等系统性错误把 API Server 打成事件喷泉。未尝试的创建必须降低 expectations。

多 Pod 时按删除排序选出目标，记录 UID/key expectations 后并发删除。删除 API 返回 NotFound 等价于目标已达成；其他失败要立即 `DeletionObserved`，否则 expectation 会一直等一个不会到来的事件。

状态更新即使 `manageReplicas` 失败也会尝试执行，因此用户能看到最新 replicas/ready/available 和失败结果。缓存对象不可原地修改，源码在更新前 `DeepCopy`。

## 3. StatefulSet：ordinal 驱动的有序状态机

入口类型 [`StatefulSetController`](../../../pkg/controller/statefulset/stateful_set.go#L66)，主循环 [`sync`](../../../pkg/controller/statefulset/stateful_set.go#L524)，算法主体 [`defaultStatefulSetControl.updateStatefulSet`](../../../pkg/controller/statefulset/stateful_set_control.go#L564)。

StatefulSet 的不变量：

| 不变量 | 例子 |
|---|---|
| 身份稳定 | `web-0` 删除重建后仍叫 `web-0` |
| ordinal 连续 | replicas=3 对应 0、1、2 |
| 存储稳定 | `data-web-0` 归属于 ordinal 0 |
| revision 可判定 | Pod label 指向 current/update revision |
| OrderedReady 时单调推进 | 前驱 Ready/Available 后才处理后继 |

控制器先生成/查找 `ControllerRevision`，再把现有 Pod 分成 `replicas` 和超出目标 ordinal 的 `condemned`。[`processReplica`](../../../pkg/controller/statefulset/stateful_set_control.go#L421) 对每个目标 ordinal 执行：终态 Pod 删除；不存在则先检查 stale PVC 再创建；Pending 时补 PVC；OrderedReady 下等待 terminating、Ready、Available；最后修复 identity/storage/retention policy。

缩容从最大 ordinal 开始处理 `condemned`。`Parallel` PodManagementPolicy 允许并发推进，但身份、存储和 retention 不变量仍必须满足。RollingUpdate 通常从高 ordinal 向低 ordinal 删除旧 revision Pod，并受 partition 控制；OnDelete 不主动替换。

[`StatefulPodControl.CreateStatefulPod`](../../../pkg/controller/statefulset/stateful_pod_control.go#L154) 先创建 PVC，再创建 Pod。PVC retention policy 通过 ownerReference 控制删除归属；它不是简单的“删除 StatefulSet 时顺便删 PVC”。

## 4. Job：完成计数、失败策略与 finalizer 协议

核心类型 [`job.Controller`](../../../pkg/controller/job/job_controller.go#L91)，主同步 [`syncJob`](../../../pkg/controller/job/job_controller.go#L909)，Pod 数量管理 [`manageJob`](../../../pkg/controller/job/job_controller.go#L1746)。

Job 有两个队列：Job key 队列和 orphan Pod 队列。Pod 可能在 Job 被删除或 selector/owner 变化后成为孤儿，单独 worker 负责重新匹配，避免主 Job 队列承担全 namespace 扫描。

主状态机需同时处理：

```text
读取 Job + claim Pods
  -> 分类 active / ready / succeeded / failed / terminating
  -> 应用 PodFailurePolicy、SuccessPolicy、backoffLimit、activeDeadline
  -> suspension 或终止条件：删除 active Pods
  -> 未完成：按 parallelism/completions 创建或删除 Pod
  -> 把新终态 Pod UID 写入 status.uncountedTerminatedPods
  -> 持久化 status
  -> 移除 Pod 的 batch.kubernetes.io/job-tracking finalizer
  -> 下一轮把 uncounted UID 折算进 succeeded/failed 计数
  -> 设置 Complete/Failed
```

finalizer 是 Job 精确计数协议的关键。若先移除 finalizer 再更新 Job status，Pod 可能被 GC 删除，终态计数永久丢失。源码在 [`trackJobStatusAndRemoveFinalizers`](../../../pkg/controller/job/job_controller.go#L1304) 和 [`flushUncountedAndRemoveFinalizers`](../../../pkg/controller/job/job_controller.go#L1483) 中先把 UID 持久化到 Job status，再并行移除 finalizer。

Indexed Job 还维护 completedIndexes、failedIndexes，并确保同一 index 的重复 Pod 只贡献一次结果。PodFailurePolicy 可以把某次失败映射为 Ignore、Count、FailJob 或 FailIndex；因此不能用“phase=Failed 就 failed++”重建。

## 5. 四者的层级关系

```text
Deployment -> ReplicaSet -> Pod
StatefulSet -> Pod + PVC + ControllerRevision
Job -> Pod（finalizer 保护终态记账）
```

上层控制器不应越层修复下层对象。Deployment 调整 RS 的声明副本数，RS 才创建 Pod。这个分层让每个 reconcile 保持单一职责，也允许 ReplicaSet 独立工作。
