# 探针、PodStatus、Volume 与优雅终止

## 1. 探针是独立反馈环

[`pkg/kubelet/prober/prober_manager.go`](../../../pkg/kubelet/prober/prober_manager.go) 的 `manager` 以 `(podUID, containerName, probeType)` 为 key 保存 worker。`AddPod` 为每个 startup/readiness/liveness probe 创建 worker goroutine；`RemovePod/CleanupPods` 关闭 worker stop channel。

探针 worker 的 context 特意与调用它的 pod worker context 解耦。原因是 Pod 开始 terminating 时 pod sync context 会取消，但 readiness 仍应有机会把终止中的 endpoint 标为 not ready。liveness/startup 则由 `StopLivenessAndStartup` 显式停止。

[`worker.go`](../../../pkg/kubelet/prober/worker.go) 的 `run` 使用 ticker，并在 kubelet 重启后先随机等待一段时间，避免所有 probe 同时打爆节点。`doProbe`：

1. 从 status manager 取最新容器 ID，容器换代时清空旧结果。
2. startup 未成功前，liveness/readiness 暂停。
3. 调 `prober.probe` 执行 exec/http/tcp/grpc。
4. 累计连续成功或失败次数。
5. 达到 `successThreshold/failureThreshold` 才发布结果。
6. liveness/startup 失败后设置 `onHold`，等待容器 ID 改变，避免反复发送重启事件。

初值不同：readiness=Failure，liveness=Success，startup=Unknown。这体现安全倾向：没有 readiness 证据就不接流量，但没有 liveness 证据不能贸然杀容器。

[`results/results_manager.go`](../../../pkg/kubelet/prober/results/results_manager.go) 同时是 cache 和边沿通知 channel；只有结果发生变化才发送 update。syncLoop 消费 liveness/startup 变化并触发 Pod sync，readiness 则调用 status manager 更新 Ready。

当前工作树对重启恢复更谨慎：已在重启前启动的 restartable init container 可给 startup result 播种 Success；readiness worker 尚未产生结果时也有专门逻辑避免把已运行容器无理由长期置为 NotReady。

## 2. status manager 的单写线程模型

[`pkg/kubelet/status/status_manager.go`](../../../pkg/kubelet/status/status_manager.go) 中：

- `podStatuses map[UID]versionedPodStatus` 是期望上报状态。
- 每次内部变化递增 `version`。
- `apiStatusVersions` 记录某 UID 已成功提交到 API 的版本，只由同步 goroutine访问。
- 容量 1 的 `podStatusChannel` 只表示“存在未同步数据”，不承载每次状态内容。

`SetPodStatus`、`SetContainerReadiness`、`SetContainerStartup`、`TerminatePod` 最终都调用 `updateStatusInternal`。它负责规范化状态、检查非法状态倒退、维护 transition time、比较是否真的变化并唤醒同步线程。

`Start` 保证 `syncPod` 与周期 `syncBatch` 在同一 goroutine 执行，避免两个 Patch 互相覆盖。`syncPod` 取 mirror/static pod 映射，调用 `statusutil.PatchPodStatus`，成功后更新 `apiStatusVersions`。网络/API 失败不会丢状态，因为内存 version 仍大于已提交 version，下一批次继续重试。

`TerminatePod` 在 runtime 已无法再提供完整状态时补齐终止状态。`canBeDeleted` 不只看 phase terminal，还询问 `PodDeletionSafetyProvider`，确保运行时容器、卷和其他节点内容已经安全清理，之后才允许删除 API Pod。

[`status/generate.go`](../../../pkg/kubelet/status/generate.go) 集中生成 Initialized、ContainersReady、Ready、PodReadyToStartContainers、AllContainersRestarting 等 condition。Ready 不是探针结果的简单复制：它还受容器状态、readiness gates、Pod phase 影响。

## 3. Volume Manager 的双缓存

[`pkg/kubelet/volumemanager/volume_manager.go`](../../../pkg/kubelet/volumemanager/volume_manager.go) 保存：

- Desired State of World：哪些 Pod 希望使用哪些 volume。
- Actual State of World：节点认为哪些 volume 已 attach/device-mount/pod-mount，或处于 uncertain。
- desired-state populator：从 pod manager、PVC、PV 生成 DSW。
- reconciler：比较 DSW 与 ASW，发起异步操作。
- operation executor：去重同一 volume/pod 上的并发操作并实施 backoff。

`Run` 分别启动 populator 和 reconciler。`WaitForAttachAndMount` 不亲自 mount，而是让 populator reprocess Pod，然后轮询 ASW，直到所有期望 volume 已挂载或超时。`SyncPod` 因而可以同步等待，底层耗时 I/O 仍由独立 goroutine 执行。

[`populator/desired_state_of_world_populator.go`](../../../pkg/kubelet/volumemanager/populator/desired_state_of_world_populator.go) 解析 inline volume 或 PVC→PV，检查 volume mode、SELinux mount context、filesystem resize，并加入 DSW。Pod 已从期望移除时也不会立刻删 DSW：若 ASW 尚无足够信息且 pod manager 仍看到 Pod，会等待，避免启动阶段误卸载。

[`reconciler/reconciler_common.go`](../../../pkg/kubelet/volumemanager/reconciler/reconciler_common.go) 的循环顺序是：卸载不再需要的 pod mount；挂载/attach 需要的 volume；扩容；卸载 device；最后 detach。顺序保证不会在仍有 Pod mount 时 detach。

## 4. uncertain 状态为何必要

mount RPC 超时并不等于 mount 没发生。若直接标记 NotMounted，重试可能重复执行危险操作；若标记 Mounted，又可能向容器暴露不存在的路径。ASW 因此支持 uncertain 状态：对“可用”判断保守为否，对 cleanup 判断保守为“可能仍挂载”。后续通过 mount table 重建和 reconcile 消除不确定性。

[`reconciler/reconstruct.go`](../../../pkg/kubelet/volumemanager/reconciler/reconstruct.go) 在 kubelet 重启后扫描磁盘 Pod volume 目录，重建 ASW，再由正常循环验证和清理。`statesHasBeenSynced` 首次完成前，不应把 NodeStatus 的 volumes-in-use 当成完整事实。

## 5. 完整优雅终止链

```text
DeletionTimestamp / eviction / probe failure
  -> podWorkers.UpdatePod(Kill)
  -> grace period 只能缩短
  -> SyncTerminatingPod
       -> 停止 startup/liveness
       -> readiness 退出流量
       -> preStop
       -> CRI StopContainer（依赖顺序）
       -> 持续写 PodStatus
  -> runtime 确认容器退出
  -> SyncTerminatedPod
       -> 等待 volume unmount
       -> 释放 CPU/内存/device/DRA
       -> 删除 Pod 内容和目录
       -> status manager 判断可安全删除
```

必须区分“请求终止”“已开始终止”“运行时已终止”“节点内容已清理”“API 对象可删除”。把它们压成一个 bool，会在重启、超时和重复删除时迅速失控。
