# 16. 测试体系：Unit、Integration、E2E、Node、Perf 与 Fuzz

## 16.1 选测试层级

| 层级 | 真实依赖 | 适合验证 |
|---|---|---|
| 同包单元测试 | fake client/clock/runtime | 算法、状态机、错误分支 |
| integration | etcd、test API server、真实组件 | storage、admission、controller/scheduler 协作 |
| e2e | 完整集群 | 用户可见跨组件契约 |
| e2e_node | Kubelet、CRI、节点系统 | probe、volume、cgroup、runtime |
| declarative validation | 新旧 validation 对照 | API 声明式校验迁移 |
| fuzz | 自动变异输入 | codec/parser/conversion 崩溃和不变量 |
| perf/benchmark | 可控规模负载 | 延迟、吞吐、内存 |
| soak | 长时间环境 | 泄漏、漂移、稳定性 |

## 16.2 单元测试

测试与源码同包。优先读 `pod_workers_test.go`、scheduler queue/cache/schedule tests、controller sync tests、proxier tests。表驱动 case 应表达初始对象、注入错误、期望 actions/status/queue state。

Fake clock 用于 backoff、lease、cron、delaying queue，避免 sleep。测试 goroutine 必须可停止，失败时 dump 队列/对象而非只超时。

## 16.3 Fake Client 与 Fixtures

client-go Fake 的 reactor 拦截 verb/resource 并返回对象或错误；Actions 用于断言调用。它不完整实现 API Server default、validation、admission、resourceVersion、subresource 和 SSA。

Fixture 可是 Go builder、YAML/JSON、embedded manifest、fake runtime state。Builder 适合类型安全边界，YAML 适合用户契约。`test/fixtures` 和 e2e testing-manifests 使用 go:embed，确保测试二进制脱离源码目录仍运行。

## 16.4 Integration Framework

`test/integration/framework/etcd.go` 管理 etcd 生命周期；`test_server.go` 创建 API Server；各 suite 的 `main_test.go` 常用 `EtcdMain(m.Run)`。测试使用真实 REST 请求、watch、storage 和 admission，再启动 scheduler/controller 等。

每个测试应隔离 storage prefix/namespace，注册 cleanup，等待最终条件而非假设 goroutine 顺序。失败信息应包含相关对象、conditions 和 events。

## 16.5 Scheduler Integration

`test/integration/scheduler` 可启动 scheduler 和 test server，创建 Nodes/Pods/claims，等待 binding 或 condition。适合测试 plugins、preemption、queue activation、volume/DRA/PodGroup。纯 scoring 细节仍应留在单元测试。

## 16.6 Controller Integration

Deployment、ReplicaSet、StatefulSet、Job、GC、Namespace、EndpointSlice 等各有 integration 目录。目标是验证真实 informer + workqueue + API conflict/default/finalizer，而不是 mock 每次 client action。

## 16.7 E2E Framework

入口 `test/e2e/e2e_test.go`，Ginkgo specs 通过 feature packages 注册。Framework 创建 namespace/client、注册 cleanup、提供等待和诊断。TestContext 承载 provider、kubeconfig、report 等全局参数。

标签标识 SIG、Feature、Conformance、Serial、Disruptive、Slow。Conformance 测试有稳定契约和发布治理，不应随意添加环境依赖。

## 16.8 E2E Node

入口 `test/e2e_node/e2e_node_suite_test.go`，可由 node test runner 准备 kubelet、runtime 和系统服务。适合 kubelet TLS、CRI、volume、device plugin、pod lifecycle、node perf。Windows 有独立 builder/services 和平台条件。

## 16.9 DRA E2E

`test/e2e/dra`、`test/e2e_dra` 和 node device plugin fixtures 覆盖 ResourceSlice/Claim、driver registration、allocation、prepare/unprepare。需要明确测试 driver 是 in-cluster controller、node plugin 还是两者。

## 16.10 性能

`test/integration/scheduler_perf` 用 workload 配置和 metrics 评估调度吞吐/延迟；node perf 观察 pod startup、resource；benchmark 包应固定规模、feature gates 和采样窗口。性能回归必须同时记录环境和 p50/p95/p99，而非单次总时长。

## 16.11 Fuzz 与序列化测试

Round-trip 测试验证 external/internal/storage conversion；fuzz 针对 JSON/CBOR/YAML、field selectors 等；compatibility fixtures 防 API wire 变化。Fuzz 发现 panic 后应缩减为稳定回归 case。

## 16.12 改动到测试的映射

- API type/default/validation：round-trip + declarative validation + apiserver integration。
- Controller reconcile：同包单测 + 对应 integration。
- Scheduler plugin/queue：framework/queue 单测 + scheduler integration。
- Kubelet runtime/volume：单测 + e2e_node。
- Service proxy：fake dataplane 单测 + network e2e。
- 用户跨组件行为：e2e。
- 生成器：golden/output diff + verify。
