# Node lifecycle、Garbage Collector 与 Namespace

## 1. Node lifecycle：健康判断与区域限速

核心类型 [`nodelifecycle.Controller`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L224)，构造函数 [`NewNodeLifecycleController`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L314)，运行入口 [`Run`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L446)。

它不是单一 workqueue worker，而是多条循环：

| 循环/队列 | 责任 |
|---|---|
| `monitorNodeHealth` | 周期检查 Lease/NodeStatus 心跳，更新 Ready condition |
| nodeUpdateQueue | NoSchedule taint 变更 |
| zoneNoExecuteTainter | 按 zone 限速施加 NoExecute taint |
| podUpdateQueue | 节点异常时更新 Pod Ready condition |

[`nodeHealthMap`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L193) 自带锁，保存 probeTimestamp、readyTransitionTimestamp 和最近观测到的 Node/Lease。读取使用 deep copy，避免持锁对象被外部修改。

[`tryUpdateNodeHealth`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L844) 判断逻辑不是“现在减最后心跳时间”这么简单。NodeStatus 和 Lease 任一推进都可作为健康信号；首次观测节点会建立 grace period。超过 `nodeMonitorGracePeriod` 后把 Ready 转为 Unknown，并对应增加 `node.kubernetes.io/unreachable` taint；明确 NotReady 使用 `node.kubernetes.io/not-ready`。

[`ComputeZoneState`](../../../pkg/controller/nodelifecycle/node_lifecycle_controller.go#L1334) 把 zone 分为 Normal、PartialDisruption、FullDisruption。大面积故障时降低或暂停 eviction QPS，防止控制面网络分区把整个业务区的 Pod 同时驱逐。小集群和大集群使用不同阈值。

注意：实际基于 tolerationSeconds 驱逐 Pod 的逻辑已由独立 taint-eviction controller 承担；Node lifecycle 主要维护 taint 和健康状态。

## 2. Garbage Collector：动态依赖图

GC 分成 GraphBuilder 和删除 worker 两部分。入口 [`GarbageCollector`](../../../pkg/controller/garbagecollector/garbagecollector.go#L64)，图构建器 [`GraphBuilder`](../../../pkg/controller/garbagecollector/graph_builder.go#L82)。

GraphBuilder 通过 discovery 获取所有支持 list/watch/delete 的 GVR，为每种资源动态建立 metadata informer。事件先进入 `graphChanges`：

```text
Add/Update/Delete metadata event
  -> processGraphChanges
  -> 以 UID 创建/更新 node
  -> 更新 owners 与 dependents 双向边
  -> owner 变化或删除时，把相关 node 放入 attemptToDelete/attemptToOrphan
```

图节点 identity 包含 apiVersion、kind、namespace、name、UID。UID 防止同名对象删除重建后误接旧边。虚拟节点表示“先看到 dependent、还没看到 owner”的情况；后续 owner 到达再合并。

[`attemptToDeleteItem`](../../../pkg/controller/garbagecollector/garbagecollector.go#L503) 会从 API Server 验证 ownerRef，不能只信图缓存。owner 引用分类为 solid、dangling、waitingForDependentsDeletion：

| 分类 | 结果 |
|---|---|
| 至少一个 solid owner | 保留 dependent |
| 全部 dangling | 删除 dependent |
| owner foreground deleting | dependent 先删，owner 等待 |
| orphan finalizer | patch dependents 去掉 ownerRef，再移除 owner finalizer |

Foreground deletion 的 `foregroundDeletion` finalizer 让 owner 在所有 blocking dependent 消失前保持 Terminating。Background deletion 允许 owner 先消失，GC 后续清 dependent。Orphan 则保留 dependent 并解除引用。

图节点 dependents 集合和 absent-owner cache 有各自同步保护。不要在持图锁时做 API 请求；源码通过队列把图变更和远程操作解耦。

## 3. Namespace：发现资源、清空内容、移除 finalizer

入口 [`NamespaceController`](../../../pkg/controller/namespace/namespace_controller.go#L54)，真正删除算法是 [`namespacedResourcesDeleter.Delete`](../../../pkg/controller/namespace/deletion/namespaced_resources_deleter.go#L96)。只对有 `DeletionTimestamp` 且仍有 `kubernetes` finalizer 的 Namespace 工作。

步骤如下：

```text
GET Namespace
  -> 把 phase 更新为 Terminating
  -> discovery 获取 namespaced、支持 delete 的 GVR
  -> 按 GVR 删除全部内容
  -> 重新 list 确认剩余对象
  -> 更新 NamespaceDeletion* conditions
  -> 若仍有对象/优雅终止时间：返回 ResourcesRemainingError，延迟重试
  -> 内容为空：调用 finalize 子资源移除 finalizer
```

[`deleteAllContentForGroupVersionResource`](../../../pkg/controller/namespace/deletion/namespaced_resources_deleter.go#L411) 优先 `DeleteCollection`，不支持时退化为 list + deleteEachItem。operation cache 记住某 GVR 不支持的动词，避免每轮重复探测。

删除请求成功不等于资源已消失。控制器必须重新 list；对象自己的 finalizer、gracePeriod、GC 依赖都可能使 Namespace 保持 Terminating。Pod 剩余时间由 [`estimateGracefulTerminationForPods`](../../../pkg/controller/namespace/deletion/namespaced_resources_deleter.go#L629) 估算。

Namespace 是“finalizer 作为分布式提交协议”的最佳示例：只有确认 namespace 内所有可发现资源为空，才提交最终步骤。
