# 11. v1.37 新路径：Generic Workload、PodGroup、组合调度与 DRA

## 11.1 为什么单 Pod 模型不够

AI/HPC、拓扑敏感和分布式任务常要求一组 Pod 共同满足最小数量或布局约束。当前源码通过 GenericWorkload、PodGroup、CompositePodGroup、GangScheduling 和 TopologyAwareWorkloadScheduling 等 feature 扩展调度实体。

这些能力仍受 feature gate/API version 控制。实现和文档必须清楚区分“源码存在”“默认启用”“稳定 API”三个层次。

## 11.2 PodGroup API

Pod 可通过 `spec.schedulingGroup.podGroupName` 关联 PodGroup。PodGroup 描述 minCount、调度超时/策略、status conditions 等。Scheduler informer 在 GenericWorkload 启用时观察 PodGroup，并在 cache 中维护 unscheduled、assumed、assigned members。

关键线索：`pkg/scheduler/eventhandlers.go`、`schedule_one_podgroup.go`、backend queue/cache 的 podgroup 状态，以及 `staging/src/k8s.io/api/scheduling` 类型。

## 11.3 PodGroup 调度周期

队列实体不再总是单个 QueuedPodInfo，也可能是 QueuedPodGroupInfo。调度器收集组成员，检查 minCount，尝试为多个 Pod 产生 placement/assignments，统一提交结果，并更新 PodGroupInitiallyScheduled condition。

失败时要区分整个组不可调度、部分 Pod scheduler error、等待 preemption 和 placement 插件失败，不能简单把所有成员独立放回 activeQ。

## 11.4 Gang Scheduling

Gang 语义强调组达到最低可行集合后共同推进，防止部分成员占资源却永远等不到其他成员。实现需要组级 admission/placement、资源预留和失败回滚。并不意味着底层 API Bind 真正原子事务，因此要设计补偿和状态可观察性。

## 11.5 CompositePodGroup 与拓扑布局

CompositePodGroup 表达多个 PodGroup 的父级组合。PlacementGenerate/PlacementScore 等扩展点可以生成拓扑布局候选并评分。Scheduler cache/queue 同时维护父子实体，事件需激活正确层级。

阅读 `schedule_one_podgroup_test.go` 可看到 GeneratePlacements、ScorePlacement、parent placement 和不同 feature gate 组合的边界。

## 11.6 Deferred Pod Scheduling

Deferred scheduling 插件用于推迟某些 Pod 的普通调度时机，与 scheduling gates、组状态或外部条件协作。返回状态必须映射到正确队列，不应通过忙等实现。

## 11.7 DRA 对象

- DeviceClass：设备选择/配置类别。
- ResourceClaim/Template：工作负载资源请求。
- ResourceSlice：节点或驱动发布的设备库存。
- DeviceTaintRule：设备级 taint 规则。

Scheduler dynamicresources plugin 结合 claim、slice、class、taint 和 CEL selector 判断可分配设备，产生 allocation。Kubelet DRA manager/plugin manager 在节点侧准备、使用和取消准备设备，并 checkpoint 状态。

## 11.8 DRA 数据流

```text
Driver publishes ResourceSlices
 -> workload references ResourceClaim
 -> controller prepares claim lifecycle
 -> scheduler Filter/Reserve evaluates allocation
 -> API records allocation
 -> kubelet sees bound Pod + Claim
 -> DRA node plugin prepares devices
 -> runtime receives device/CDI information
 -> Pod termination unprepares according to lifecycle
```

## 11.9 Device Taint Eviction

当前 `pkg/controller/devicetainteviction` 观察 Pod、ResourceClaim、ResourceSlice、DeviceTaintRule、DeviceClass，根据设备不可用/taint 与容忍关系推进驱逐。它把传统 Node taint 思路扩展到被 claim 使用的设备。

## 11.10 重建建议

先完成单 Pod 调度，再实现简单 PodGroup minCount；随后加入组级 placement 和回滚；最后实现 DRA 的 inventory/claim/allocation/prepare 状态机。不要同时引入组合组、拓扑评分和真实设备插件，否则无法隔离一致性错误。
