# 17. Codegen、Update、Verify、Build 与 Release

## 17.1 仓库约束

生成文件只读；`go.mod/go.work` 由脚本维护；staging 是 `k8s.io/*` 权威源码；每个 Go 文件需要 license boilerplate。依赖修改使用 `hack/pin-dependency.sh` 和 `hack/update-vendor.sh`，不能直接 `go mod tidy`。

## 17.2 API 生成链

输入是 API Go types、package markers、field tags 和 scheme registration。`hack/update-codegen.sh` 组织：DeepCopy、conversion、default、validation、register、protobuf、OpenAPI、typed clients、apply configurations、listers、informers 等。

```text
types + markers
 -> runtime helpers
 -> wire/schema artifacts
 -> clients/apply
 -> listers/informers
 -> API compatibility/discovery/OpenAPI fixtures
```

生成文件改动必须能由输入变化解释。手改生成物会在下一次 update 消失。

## 17.3 Declarative Validation

当前 `test/declarative_validation` 覆盖各 API group 的声明式 validation 迁移。生成/声明规则与手写 validation 可在迁移期双跑比较。新增规则要处理 old object、subresource、feature gate 和版本转换。

## 17.4 OpenAPI 与 Discovery

`api/openapi-spec` 保存 v2/v3 快照，`api/discovery` 保存 discovery 契约。`hack/update-openapi-spec.sh` 启动/访问 API Server 抓取输出；verify 比较仓库快照。OpenAPI 的 `x-kubernetes-*` 决定 apply/list/map 等语义。

## 17.5 API Compatibility

Generated compatibility data和 lifecycle tests 检查字段、版本、protobuf 和存储兼容。API 规则例外位于 `api/api-rules`，例外不是绕过评审的快捷方式，而是有历史原因的显式债务。

## 17.6 make update

根 Makefile 委托 `build/root/Makefile` 和 `hack/make-rules/update.sh`。完整 update 包含 codegen、feature gates、compatibility data、docs、OpenAPI、gofmt、lint config 等。局部脚本可加速开发，但提交前要根据变更覆盖完整目标。

## 17.7 make verify

`hack/make-rules/verify.sh` 发现 verify scripts，可用 WHAT/QUICK 控制范围。典型检查：codegen diff、gofmt、imports、boilerplate、lint、API groups、feature gates、metrics、licenses、vendor、staging metadata、conformance 和依赖。

Verify-generated 常在临时目录重跑生成并 diff。失败应定位输入/工具版本，不要只删除差异。

## 17.8 Vendor

`hack/update-vendor.sh` 同步 root/staging 模块、vendor/modules.txt 和 workspace 信息；verify-vendor 重建对比。发布 staging 模块依赖 import restrictions 和 publishing rules。

## 17.9 构建

`hack/make-rules/build.sh`/`hack/build-go.sh` 调用 Go 构建；`build/common.sh` 提供容器化 builder 和跨平台环境。输出通常位于 `_output`。`make` 构建核心目标，quick-release 使用本地快速路径，release 使用可复现容器环境。

## 17.10 发布制品

`build/release.sh` 和 `build/lib/release.sh` 产生 source、server、node、client、test、manifests tarballs 及多架构镜像。镜像基于 `build/server-image` 等定义。package-tarballs 可复用已有二进制，release-images 聚焦镜像。

## 17.11 Staging 发布

`staging/publishing/rules.yaml` 定义独立仓库发布和依赖顺序，publishing bot 将 authoritative staging 内容同步到 GitHub 模块仓库。新增 staging repo 还要更新 import restrictions、README、模板和外部发布配置。

当前 staging 列表包括新的 `k8s.io/streaming` 等模块，说明 streaming 边界继续从组件内部抽离。

## 17.12 Cluster 脚本

`cluster/kube-up.sh -> provider util -> validate-cluster.sh` 展示历史集群创建；kube-down 要幂等清理；GCE 是主要实现；skeleton 定义 provider 函数。新增生产部署不建议复制该维护模式体系，但它适合学习制品、配置和生命周期编排。

## 17.13 贡献闭环

1. 明确手写输入文件。
2. 修改实现与最小相关测试。
3. API/marker 变化运行对应 update。
4. 检查生成 diff 是否合理。
5. 运行最小 unit/integration。
6. 运行相关 verify。
7. 按发布影响扩大验证。
