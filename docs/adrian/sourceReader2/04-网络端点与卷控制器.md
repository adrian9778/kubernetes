# EndpointSlice 与 Volume 控制器

## 1. EndpointSlice：Pod 到 Service 的投影

核心类型 [`endpointslice.Controller`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L193)，构造函数 [`NewController`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L85)，Service 同步 [`syncService`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L368)。

当前实现有三条队列：

| 队列 | key | 目的 |
|---|---|---|
| `podQueue` | `PodProjectionKey` | 延迟做 Pod labels/namespace 到 Service 的映射 |
| `serviceQueue` | `namespace/name` | 计算并写 EndpointSlice |
| `topologyQueue` | 常量 key | Node Ready/zone 变化后重算 topology cache |

Pod 更新不会在 informer callback 中遍历所有 Service，而是生成只包含投影相关字段的 key。[`syncPod`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L488) 找到受影响 Service，再按 `endpointUpdatesBatchPeriod` 放入 serviceQueue。这既降低 handler 延迟，也合并频繁 Pod status 更新。

[`syncService`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L368) 的步骤：

```text
读 Service
  -> NotFound：清 trigger/tracker/reconciler 状态
  -> ExternalName 或 selector=nil：忽略
  -> selector 列出 Pods
  -> label 列出本控制器管理的 EndpointSlices
  -> 丢弃 DeletionTimestamp != nil 的 slice
  -> EndpointSliceTracker 检查 informer 是否落后于预期 RV
  -> 计算 last-change-trigger-time
  -> Reconciler.Reconcile：create/update/delete slices
```

`EndpointSliceTracker` 与 expectations 类似，但追踪的是每个 slice 的 resourceVersion 和预期删除。若缓存落后，返回 `StaleInformerCache` 重试，避免用旧 slice 集合重复创建。

Node zone/Ready 改变只进入单 key topologyQueue；[`checkNodeTopologyDistribution`](../../../pkg/controller/endpointslice/endpointslice_controller.go#L631) 更新 topology cache，并仅重新排队超过分布阈值的 Service。

## 2. PV/PVC Binder：双向绑定状态机

核心类型 [`PersistentVolumeController`](../../../pkg/controller/volume/persistentvolume/pv_controller.go#L144)，构造入口 [`NewController`](../../../pkg/controller/volume/persistentvolume/pv_controller_base.go#L77)。它维护独立的 volumeQueue 和 claimQueue，主同步分别是 [`syncVolumeByKey`](../../../pkg/controller/volume/persistentvolume/pv_controller_base.go#L541) 与 [`syncClaimByKey`](../../../pkg/controller/volume/persistentvolume/pv_controller_base.go#L611)。

PVC 主状态：

| 状态 | 关键动作 |
|---|---|
| 未绑定且 `spec.volumeName` 为空 | 查最佳 PV；无匹配则 dynamic provision 或等待 scheduler selected-node |
| 预绑定到 PV | 校验 PV，补全双向绑定 |
| Bound | 校验 PV.ClaimRef UID 与 PVC.volumeName，修复 status |
| 对象删除 | 清理 cache，唤醒对端 |

绑定是两步：先写 `PV.spec.claimRef`，再写 `PVC.spec.volumeName`，最后更新双方 status。源码 [`bind`](../../../pkg/controller/volume/persistentvolume/pv_controller.go#L1095) 必须容忍任一步成功后进程崩溃；下一轮根据已有字段继续完成，而不是回滚成“未发生”。ClaimRef 使用 UID，防止同名 PVC 重建后继承旧 PV。

PV 释放后依据 reclaimPolicy 执行 Retain、Delete 或旧式 Recycle。Delete 路径要处理 in-tree/CSI migration finalizer；只有底层存储删除完成，才能移除 PV deletion protection finalizer。

`WaitForFirstConsumer` 把拓扑选择交给 scheduler 的 VolumeBinding 插件。scheduler 先为 PVC 写 selected-node/assume binding，PV controller 或外部 provisioner 再创建/绑定卷；因此卷调度不是单一控制器内部流程。

## 3. Attach/Detach：DSW 与 ASW 的周期对账

入口 [`attachDetachController`](../../../pkg/controller/volume/attachdetach/attach_detach_controller.go#L247)，运行函数 [`Run`](../../../pkg/controller/volume/attachdetach/attach_detach_controller.go#L334)，核心周期循环 [`reconciler.reconcile`](../../../pkg/controller/volume/attachdetach/reconciler/reconciler.go#L165)。

内存模型：

| 状态 | 含义 |
|---|---|
| DesiredStateOfWorld | 从 scheduled Pod、PVC/PV、Node 计算“卷应附着到哪里” |
| ActualStateOfWorld | 从 Node status、VolumeAttachment 和 operation result 计算“当前附着情况” |
| OperationExecutor | 去重并异步执行 attach/detach，记录 pending operation/backoff |

DesiredStateOfWorldPopulator 消费 informer 事件，不直接执行 attach。Reconciler 周期比较 DSW/ASW：DSW 有而 ASW 无则 attach；ASW 有而 DSW 无、且节点健康/安全条件满足则 detach。这样即使事件丢失，周期对账仍能收敛。

多节点同时请求不支持 multi-attach 的卷时不应盲目 attach；[`reportMultiAttachError`](../../../pkg/controller/volume/attachdetach/reconciler/reconciler.go#L376) 给相关 Pod 发事件。节点 OutOfService taint 会改变强制 detach 判断，防止故障节点永久占有卷。

## 4. Protection finalizer

PVC protection controller 在仍被 Pod 使用时保留 `kubernetes.io/pvc-protection`。PV protection 和 VAC protection 同理。它们体现一个规则：API 对象的删除时间戳只表示“删除协议开始”，finalizer 清空才表示协议完成。
