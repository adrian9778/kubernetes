# 主链路逐步拆解

> **层级**：第三层——基于 `kubectl run nginx --image=nginx --restart=Never`，把主链路逐跳拆解，每跳说明调用双方、参数传递与转换、内部动作、返回值去向、状态变化、数据流转与错误传播。
>
> **代码基准**：`master@8893923938107170c86eb4b8cc2b7225b4e44e9b`（2026-11-18，工作区干净），Go 1.27.4。
>
> **锚点记法**：源码锚点一律「符号 + 偏移」。函数内偏移以该函数声明行为 **+0**；例如 `frameworkImpl.RunFilterPluginsWithNominatedPods`（定义行 1467）写作 `frameworkImpl.RunFilterPluginsWithNominatedPods:1467/+0`。行号仅供定位函数，不单独作为锚点。

## 0. 全链路时序

```mermaid
sequenceDiagram
    participant U as kubectl
    participant A as apiserver
    participant E as etcd
    participant S as scheduler
    participant K as kubelet
    participant R as 容器运行时(CRI)
    U->>A: POST /api/v1/namespaces/default/pods
    A->>A: 认证/审计/impersonation/流控/鉴权 + mutating admission + 校验 + validating admission
    A->>E: OptimisticPut /registry/pods/default/nginx (expectedRev=0)
    A-->>U: 201 Pod(nodeName="")
    E-->>S: watch 事件(新 Pod, nodeName="")
    S->>S: Filter + Score(同步调度周期)
    S->>S: Assume(调度缓存)
    S->>A: bind(异步绑定周期, 更新 spec.nodeName)
    A->>E: 更新 spec.nodeName
    E-->>K: watch 事件(本节点 Pod)
    K->>R: RunPodSandbox
    K->>R: CreateContainer / StartContainer
    R-->>K: 容器状态
    K->>A: PATCH pod status(Running)
```

参与者即真实组件：`kubectl`（客户端）、`apiserver`（kube-apiserver 聚合端点）、`etcd`（持久化与 watch 广播）、`scheduler`（kube-scheduler）、`kubelet`（节点代理）、`容器运行时(CRI)`（经 gRPC 的 containerd 等）。

#### 状态回报机制深度拆解

状态回报不是「容器一启动就上报」，而是 kubelet 侧一条独立的异步上报管线，核心是 `pkg/kubelet/status/status_manager.go` + `pkg/util/pod/pod.go`。

**收集与去抖（`updateStatusInternal`，status_manager.go:1024）：**
1. 取缓存旧状态：`m.podStatuses[pod.UID]`（无缓存则退回 mirrorPod.Status 或 pod.Status）。
2. **非法状态迁移检查**：`checkContainerStateTransition`（+23 附近）拦截非法的容器状态回退，命中则中止本次更新。
3. 逐 condition 调 `updateLastTransitionTime`（ContainersReady/Ready/Initialized/PodReadyToStartContainers/PodScheduled/DisruptionTarget/AllContainersRestarting）：**只在状态实际变化时刷新 LastTransitionTime**，避免无意义的时间戳跳动。
4. 保持 `StartTime` 跨更新不变。

**批量上报（`Start`，status_manager.go:285）：**
- `syncPod` 与 `syncBatch` **共享同一 goroutine**（注释：避免 sync race）。
- 两个触发源：`m.podStatusChannel`（有更新，`syncBatch(false)` 仅同步有变化的）+ `syncTicker`（周期 `syncPeriod`，`syncBatch(true)` 同步全部）。
- `kubeClient == nil`（master 上的 kubelet 负责引导 master 组件 Pod）时不启动 status manager。

**PATCH 上报（`syncPod`，status_manager.go:1352）：**
1. `kubeClient.Get` 取服务端最新 Pod；**NotFound 直接忽略**（Pod 已删，status 会被 `RemoveOrphanedStatuses` 清理）。
2. **UID 翻译与新建检测**：`TranslatePodUID` 后若与传入 uid 不一致 → 判定「Pod 被删后重建」，`deletePodStatus(uid)` 丢弃本次更新（防旧 status 写到新 Pod 上）。
3. `mergePodStatus` 合并服务端现状与本地 status（`PodCouldHaveRunningContainers` 参与判断）。
4. **`PatchPodStatus`** 发 PATCH。

**PATCH 的精确性（`PatchPodStatus`，pkg/util/pod/pod.go:34）：**
1. `preparePatchBytesForPodStatus`（:63）用 `CreateTwoWayMergePatch(oldData, newData, v1.Pod{})` 生成 **StrategicMergePatch**。
2. **关键细节**：`newData` 只在 ObjectMeta 里放 `uid`（注释：`only put the uid in the new object to ensure it appears in the patch as a precondition`）——使 uid 成为 PATCH 的**前置条件**，服务端校验 uid 匹配才应用。
3. **unchanged 判定**（:78 ～ +80）：若 patch 等于 `{"metadata":{"uid":<uid>}}`（即只有 uid、无 status 差异），返回 `unchanged=true`，调用方跳过网络调用。
4. 真正的 PATCH 走 `Pods(namespace).Patch(..., StrategicMergePatchType, patchBytes, ..., "status")`（:46 ～ +48）——**只 patch status 子资源**。

**设计要点（源码可证）：**
1. **异步批量而非同步阻塞**：状态上报与容器启动解耦，syncPod/syncBatch 单 goroutine 串行，容器执行不被上报耗时阻塞。
2. **双触发（事件 + 周期）**：channel 触发保证变更及时上报，ticker 兜底保证不丢（`syncBatch(true)` 全量对账）。
3. **PATCH 而非 PUT + uid 前置条件**：只 patch status 子资源、以 uid 为 precondition，避免覆盖 spec、避免把 status 写到已重建的同名 Pod 上。
4. **unchanged 短路**：无差异时不发网络请求，显著减少 apiserver 负载（大量 Pod 稳定运行时）。
5. **冲突安全**：StrategicMergePatch + status 子资源 + uid precondition 三重保证并发安全，冲突由 apiserver 侧判定。
