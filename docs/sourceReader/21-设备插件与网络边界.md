## 0. 结论速览
Kubelet 通过 gRPC 协议与设备插件和容器运行时交互，并不直接调用 CNI：`Allocate` 将设备传给 CRI，`RunPodSandbox` 把网络参数交给运行时，最终的网络插件（CNI）在运行时容器内生效。

要点：
1. **设备插件与 kubelet 的边界**：插件实现 `deviceplugin.DevicePlugin` 接口，向 kubelet 注册并推送 ListAndWatch 设备列表。
2. **设备分配动作**：kubelet 的 ManagerImpl 在调谐后调用 `Allocate`，经 `GetDeviceRunContainerOptions` 产出设备（Device/Mounts/Envs/Annotations/CDIDevices）进入 CRI。
3. **CNI 归属**：Pod 网络由容器运行时根据 PodSandboxConfig（PortMappings/NamespaceOptions/DnsConfig）在运行时侧调 CNI 完成（`pkg/kubelet` 没有 CNI 调用）。
4. **拓扑约束**：`filterByAffinity` 连接 Topology Manager 的 NUMA hint 和设备选择。
5. **checkpoint 更新**：`readCheckpoint/writeCheckpoint` 保持重启后设备分配状态可恢复。

### 3b. device plugin 三步 gRPC 流解剖（第二层补充视角）

设备插件与 kubelet 之间是**三条独立的 gRPC 通道**：注册（plugin→kubelet）、ListAndWatch（kubelet→plugin，长连接流）、Allocate（kubelet→plugin，按需）。本节解剖每条通道的发起方、请求/响应与失败语义。

#### 通道 1：Register（plugin → kubelet）

**源码：** `plugin/v1beta1/server.go Register+0`（:159）
```text
plugin 启动 → 连 kubelet 的 /var/lib/kubelet/plugins_registry/<socket>
  → 调 Register(RegisterRequest{ResourceName, Endpoint, Version})
```
- **kubelet 侧校验**（Register :162 ～ :176）：
  1. `isVersionCompatibleWithPlugin(r.Version)`（:183）：版本须在 `api.SupportedVersions`（v1alpha1/v1beta1）内，否则报 `errUnsupportedVersion`。
  2. `IsExtendedResourceName(r.ResourceName)`（:188）：资源名须是合法扩展资源名（如 `example.com/gpu`），否则报 `errInvalidResourceName`。
  3. 通过则 `connectClient(ctx, ResourceName, socketDir/Endpoint)`（:192）——kubelet 主动连插件的 endpoint socket，建 `endpointImpl`。

**关键：** Register 是**插件主动找 kubelet**（插件是 gRPC client，kubelet 是 server）；后续 ListAndWatch/Allocate 则反过来（kubelet 是 client，插件是 server）。

#### 通道 2：ListAndWatch（kubelet → plugin，服务端流式长连接）

**源码：** `plugin/v1beta1/client.go` ListAndWatch 调用（:86）
```text
stream, err := c.client.ListAndWatch(context.TODO(), &api.Empty{})
for {
    response, err := stream.Recv()        ← 阻塞等插件推送设备列表
    c.handler.PluginListAndWatchReceiver(logger, c.resource, response)
}
```
- **服务端流式**：插件持续推送 `ListAndWatchResponse{Devices[]}`（设备 ID、健康状态），kubelet 阻塞 `Recv()` 接收。
- 每次 `response` 经 `PluginListAndWatchReceiver`（manager.go:322）→ `genericDeviceUpdateCallback`（:326）更新节点上报容量与设备健康。
- **注意**：`context.TODO()`（:86，注释 FIXME）——故意不传可取消 context，使 ListAndWatch 不随单次操作取消（否则 `TestDevicePluginReRegistration` 会因 context cancelled 失败）。
- **断流语义**：`stream.Recv()` 出错 → 记日志并 return，endpoint 标记 stopped；插件重连时走重新 Register。

#### 通道 3：Allocate（kubelet → plugin，按需一元调用）

**源码：** `endpoint.go endpointImpl.allocate+0`（:113）
```text
Allocate(AllocateRequest{ContainerRequests: [{DevicesIds: devs}]})
  → AllocateResponse{Envs, Mounts, Devices, Annotations, CDIDevices}
```
- kubelet 在 Pod 调谐的 Allocate 阶段，把**选定的设备 ID 列表**发给插件。
- 插件返回该容器所需的**环境变量、挂载、设备节点、注解、CDI 设备**——这些进入 CRI container config（见 §5）。
- **前置**：`e.isStopped()`（:111）——endpoint 已停（插件断开）则返回 `errEndpointStopped`。
- **超时**：`PreStartContainer` 用 `KubeletPreStartContainerRPCTimeoutInSecs` 超时（:124）。

#### 三通道对照

| 通道 | 发起方 | 类型 | 触发 | 失败语义 |
|---|---|---|---|---|
| Register | 插件 → kubelet | 一元 | 插件启动 | 版本/资源名校验失败 → 拒绝注册 |
| ListAndWatch | kubelet → 插件 | 服务端流式长连接 | 注册成功后 | 断流 → endpoint stopped，插件重连重注册 |
| Allocate | kubelet → 插件 | 一元（按需） | Pod 调谐 Allocate 阶段 | endpoint stopped / 超时 → 分配失败 |

**设计要点（源码可证）：**
1. **注册与数据面方向相反**：Register 是插件→kubelet（插件做 client），ListAndWatch/Allocate 是 kubelet→插件（插件做 server）——两条 gRPC 连接方向相反，是设备插件最常见的连接错误来源。
2. **ListAndWatch 用 context.TODO()**：故意不可取消，使设备列表推送不随单次操作中断（client.go:84 FIXME）。
3. **设备以 ID 标识、 Allocate 才换实体**：ListAndWatch 只推设备 ID；Allocate 才把 ID 换成实际的环境变量/挂载/设备节点——kubelet 不缓存设备实体细节。
4. **endpoint stopped 兜底**：`isStopped()` 在每次 Allocate/PreStart 前检查，插件断开时快速失败而非挂起。

## 4. 分配与重新分配——函数级
`ManagerImpl.Allocate` (manager.go 函数：Allocate 偏移：+425)：
- 仅支持 `lifecycle.AddOperation`（其他 operation 直接 return nil）。
- 维护 `devicesToReuse`（每次只保留当前 pod，清掉其它 podUID）。
- **init container 先分配**：遍历 `pod.Spec.InitContainers` 匹配后调 `allocateContainerResources`；restartable init container 把设备从 `devicesToReuse` 移除（保留占用），非 restartable 则 `addContainerAllocatedResources`。
- app container：`allocateContainerResources` 后 `removeContainerAllocatedResources`。

`allocateContainerResources` (manager.go 偏移：+959)：算 `devicesToAllocate` → 逐插件经 endpoint 发 Allocate RPC → 结果写 `podDevices`。
`filterByAffinity` (manager.go 偏移：+858)：按 Topology Manager 的 NUMA hint 过滤候选设备（三组返回：preferred/allocated/others）。
`GetTopologyHints` (topology_hints.go 偏移：+34)：向 Topology Manager 提供每插件设备的 NUMA 亲和 hint。
`endpoint.allocate` (endpoint.go 偏移：+109)、`preStartContainer` (偏移：+121)。

`GetDeviceRunContainerOptions` (manager.go 偏移：+1085)：取回分配的设备；**DRA 扩展资源跳过**（feature gate `DRAExtendedResource` + `isDRAExtendedResource`，避免同名 device-plugin 缓存误用）；逐资源 `callPreStartContainerIfNeeded`；Pod 已不在 activePods 则跳过重分配；缓存丢失（节点重启 race）时置 `needsReAllocate` 重新 Allocate。

`GetCapacity` (manager.go 偏移：+511)：节点总容量与可分配容量。
checkpoint：`writeCheckpoint` (偏移：+569)、`readCheckpoint` (偏移：+590)、`getCheckpoint` (偏移：+618)。

## 5. 设备进入 CRI config
`pkg/kubelet/cm/container_manager_linux.go` 的 `containerManagerImpl.GetResources`（`:737`）调 `deviceManager.GetDeviceRunContainerOptions`（manager.go :1085），得到 `DeviceRunContainerOptions{Devices, Mounts, Envs, Annotations, CDIDevices}`，拷入 `kubecontainer.RunContainerOptions`（`:756` 左右）。

`kuberuntime_container.go` :379 经 `makeDevices`（`kuberuntime_container.go:498`）转设备，`makeCDIDevices`（`:514`）处理 CDI 设备；`:397` 起处理 Envs/Annotations。字段进入 `runtimeapi.CreateContainerRequest.Config`，运行时据此把设备节点 bind 进容器并调用 CDI 注入。

## 6. 网络边界——kubelet 不直接调 CNI
- `pkg/kubelet` 下只有注释提及 CNI，没有 CNI 库调用；实际调用发生在容器运行时内部：CRI 收到 `RunPodSandbox` 后由网络插件配置 Pod 网络。
- 网络代码现状：`pkg/kubelet/network/dns/`（dns.go、dns_other/windows.go）为 Pod 生成 DNS 配置 `runtimeapi.DNSConfig`，由 `kuberuntime_sandbox.go:98` 的 `GetPodDNS` 取用；kubelet 无 `NetworkPlugin` 实现；`pkg/kubelet/network/kubenet/` 已删除（代码移除），非 vendor 的 kubenet 引用只剩 `cluster/` 历史脚本与测试节点工具。

## 7. PodSandboxConfig 网络参数
`generatePodSandboxConfig`（`kuberuntime_sandbox.go:83`）：
- `DnsConfig`（`:103`-`107`）来自 `runtimeHelper.GetPodDNS`
- `Hostname`（`:103`）非 hostNetwork 时从 Pod 设置
- `PortMappings`（`:127`-`:144`）来自 `kubecontainer.MakePortMappings`（`pkg/kubelet/container/helpers.go:461`，containerPort/hostPort/protocol）
- Linux `NamespaceOptions`（`:142`）进入 `generatePodSandboxLinuxConfig`（`:172`）

`generatePodSandboxLinuxConfig`（`:172`）调 `runtimeutil.NamespacesForPod`（`:201`；`kuberuntime/util/util.go:111`），按 hostNetwork/hostPID/hostIPC 与 runtimeClass 决定 NET/PID/IPC namespace mode，赋给 `lc.SecurityContext.NamespaceOptions`（`:206`）。Windows 对应 `generatePodSandboxWindowsConfig`（`:248`）。

## 8. 边界总览（文字）
```
kubelet 职责                              容器运行时（CRI 实现）职责
Pod DNS 配置        ─┐
Port mappings       ─┤ RunPodSandbox(PodSandboxConfig)
namespace options   ─┘
                          ├─ 创建/加入 network namespace
                          ├─ 调 CNI 插件（ADD：veth/IP/路由）
                          └─ 回报 Pod IP（PodSandboxStatus）
kubelet 经 PodSandboxStatus 读到 IP 后写入 status（见 09 篇）
```

## 9. 调用关系总览（文字）
```
设备：插件 Register(server.Register) → ListAndWatch(genericDeviceUpdateCallback)
 Pod 调度到节点 → Allocate(filterByAffinity, endpoint.allocate)
  → GetDeviceRunContainerOptions → makeDevices/makeCDIDevices → CreateContainer
网络：NamespacesForPod + GetPodDNS + MakePortMappings
  → generatePodSandboxConfig → RunPodSandbox → 运行时侧 CNI
```
