# 设备插件与网络边界
> **层级**：第四层——函数级源码解析。
> **范围**：kubelet 设备管理器与设备插件 API、设备分配进入 CRI config 的链路；kubelet 与 CNI 的职责边界及 PodSandboxConfig 网络参数。

## 第一部分：设备插件

### 1. 模块级
| 项 | 内容 |
|---|---|
| 设备管理 | `pkg/kubelet/cm/devicemanager/`：manager.go、endpoint.go、topology_hints.go、checkpoint/、plugin/v1beta1/ |
| 插件 API | `[staging] k8s.io/kubelet/pkg/apis/deviceplugin/{v1alpha,v1beta1}/`（kubelet 使用 v1beta1，alias pluginapi） |
| 数据流 | 插件 Register → ListAndWatch 推送设备列表 → Pod 请求扩展资源 → Allocate RPC → 设备/挂载/环境变量写入 CRI container config |

### 2. 类型级
| 类型 | 文件 | 职责 |
|---|---|---|
| `ManagerImpl` | `devicemanager/manager.go`（构造 NewManagerImpl:145，内部 newManagerImpl:153） | 设备管理实现：插件 endpoint、设备健康、分配状态、checkpoint |
| `Manager`（interface） | `devicemanager/types.go:38` | Allocate:47、AllocatePod:93、GetDeviceRunContainerOptions:60、GetCapacity、UpdateAllocatedDevices:96 |
| `endpointImpl` | `devicemanager/endpoint.go:53` | 单个插件连接：allocate:109、preStartContainer:121 |

### 3. 注册与 ListAndWatch 函数级

#### 函数：plugin manager gRPC 服务端
**源码：** `devicemanager/plugin/v1beta1/server.go:67 NewServer`，Start:86
**注册服务：** `api.RegisterRegistrationServer(s.grpc, s)`（:117）；`server.Register`（:159）处理插件 Register RPC：校验 socket 与 resource name，建 endpoint 并启动其 ListAndWatch 客户端。

#### 函数：NewPluginClient / Run
**源码：** `devicemanager/plugin/v1beta1/client.go:58 / :82`
**机制：** 向插件发起 `ListAndWatch` 长连接（:86），插件周期性推送设备列表与健康状态；响应经回调 `PluginListAndWatchReceiver`（manager.go:300）→ `genericDeviceUpdateCallback`（:304）更新节点上报容量与设备健康。

### 4. 分配函数级

#### 函数：ManagerImpl.Allocate / allocateContainerResources
**源码：** `manager.go:403` / :925
**执行流程：**
1. 从 Pod 的容器扩展资源请求算出 devicesToAllocate（:618）
2. `filterByAffinity`（:824）按 Topology Manager 选定的 NUMA hint 过滤候选设备
3. 逐插件经 endpoint `allocate`（endpoint.go:109，调用点 manager.go:990）发 Allocate RPC，插件返回设备节点、挂载、环境变量、注解（含 CDI 设备）
4. 结果写入 checkpoint（重启恢复，readCheckpoint:556）

#### 函数：GetTopologyHints
**源码：** `topology_hints.go:34`
**职责：** 向 Topology Manager 提供每插件设备的 NUMA 亲和 hint；拓扑裁定结果再经 filterByAffinity 回到具体设备选择，使设备分配与 CPU/内存在同一 NUMA 节点对齐。

### 5. 设备进入 CRI config 函数级
1. `containerManagerImpl.GetResources`（`pkg/kubelet/cm/container_manager_linux.go:737`）调 `deviceManager.GetDeviceRunContainerOptions`（manager.go:1051），得到 `DeviceRunContainerOptions{Devices, Mounts, Envs, Annotations, CDIDevices}`，拷入 `kubecontainer.RunContainerOptions`（:756 ～ +761）。
2. `kuberuntime_container.go:379` 经 `makeDevices`（:457）把 `opts.Devices` 转成 `[]*runtimeapi.Device`（容器内路径映射 + 读写权限）；`:380 makeCDIDevices` 处理 CDI 设备；`:397` 起处理 Envs/Annotations。
3. 字段进入 `runtimeapi.CreateContainerRequest.Config`，容器运行时据此把设备节点 bind 进容器并调用 CDI 注入。

## 第二部分：网络边界

### 6. kubelet 不直接调用 CNI（源码确认）
非测试代码中 `pkg/kubelet` 下只有注释提及 CNI（metrics.go:363、pod_startup_latency_tracker.go:161、kuberuntime_manager.go:1725），没有 CNI 库调用。CNI 的实际调用发生在容器运行时的 CRI 实现内部：CRI 收到 RunPodSandbox 后由其网络插件配置 Pod 网络（创建 veth、分配 IP、挂网卡、写路由）。

### 7. kubelet 侧网络代码现状
| 路径 | 现状 |
|---|---|
| `pkg/kubelet/network/dns/`（dns.go、dns_other/windows.go） | 为 Pod 生成 DNS 配置 `runtimeapi.DNSConfig`，由 `kuberuntime_sandbox.go:98 GetPodDNS` 取用 |
| `NetworkPlugin` 实现 | 无残留（rg 无命中） |
| `pkg/kubelet/network/kubenet/` | **目录已删除**（代码移除）；非 vendor 的 kubenet 引用只剩 `cluster/` 历史脚本与测试节点工具 |

### 8. PodSandboxConfig 网络参数函数级

#### 函数：generatePodSandboxConfig
**源码：** `pkg/kubelet/kuberuntime/kuberuntime_sandbox.go:82`
**网络相关字段：**
| 字段 | 位置 | 来源 |

| `DnsConfig` | :98 | GetPodDNS（cluster DNS nameserver/search/options，见 network/dns） |

| Linux `NamespaceOptions` | :142 → generatePodSandboxLinuxConfig:167 | 见下 |

#### 函数：generatePodSandboxLinuxConfig
**源码：** `kuberuntime_sandbox.go:167`
**调用：** `runtimeutil.NamespacesForPod(ctx, pod, m.runtimeHelper, m.runtimeClassManager)`（:201；实体 `kuberuntime/util/util.go:112`），按 hostNetwork/hostPID/hostIPC 与 runtimeClass 决定 NET/PID/IPC namespace mode，赋给 `lc.SecurityContext.NamespaceOptions`（:206）。Windows 对应 `generatePodSandboxWindowsConfig`（:243）。

### 9. 边界总览
```text
kubelet 职责                          容器运行时（CRI 实现）职责
Pod DNS 配置        ─┐
Port mappings       ─┤ RunPodSandbox(PodSandboxConfig)
namespace options   ─┘
                         ├─ 创建/加入 network namespace
                         ├─ 调 CNI 插件（ADD：veth/IP/路由）
                         └─ 回报 Pod IP（PodSandboxStatus）
kubelet 经 PodSandboxStatus 读到 IP 后写入 status（见 09 篇）
```

## 10. 调用关系总览
```text
设备：插件 Register(server.Register) → ListAndWatch(genericDeviceUpdateCallback)
 Pod 调度到节点 → Allocate(filterByAffinity, endpoint.allocate)
  → GetDeviceRunContainerOptions → makeDevices/makeCDIDevices → CreateContainer
网络：NamespacesForPod + GetPodDNS + MakePortMappings
  → generatePodSandboxConfig → RunPodSandbox → 运行时侧 CNI
```

## 11. 仓库边界
第三方内容不在本仓库：具体设备插件（GPU/FPGA 等）与 CDI 规范实现、具体 CNI 插件与 IPAM、容器运行时内部的网络管理。本仓库给出注册协议、分配协议与配置参数，扩展点全部以 socket/gRPC 形式接入。
